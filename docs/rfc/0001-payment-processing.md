# RFC 0001. Асинхронный процессинг платежей

**Статус:** на согласовании
**Дата:** 2026-08-14

Документ фиксирует решения, границы и контракты до написания кода. После согласования
не переписывается — изменения идут через ADR в `docs/adr/`.

---

## 1. Контекст и цель

Сервис принимает запросы на оплату, ставит их в очередь, обрабатывает через эмуляцию
внешнего платёжного шлюза и уведомляет клиента о результате через webhook.

Синхронная часть (HTTP) обязана быть быстрой и не зависеть от доступности брокера: приём
платежа считается состоявшимся в момент коммита в БД, а не в момент публикации события.

---

## 2. Гарантия доставки

**Принимаем at-least-once на всех трёх участках:** outbox → брокер, брокер → consumer,
consumer → webhook получателя.

Exactly-once недостижим: между вызовом внешнего шлюза и записью результата в БД всегда
существует окно, в котором процесс может умереть. Мы не пытаемся его закрыть — мы делаем
повтор безопасным.

Прямые следствия, обязательные к реализации:

1. **Consumer идемпотентен.** Повторная доставка того же события не приводит к повторному
   обращению к шлюзу и не меняет уже терминальный статус.
2. **Эмуляция шлюза полностью детерминирована по `payment_id`** — и исход, и длительность.
   Исход вычисляется как функция от идентификатора, а не через `random()` в момент вызова:
   иначе две параллельные обработки дубля дадут противоречащие результаты, и клиент получит
   два взаимоисключающих уведомления. Длительность выводится из того же идентификатора и
   отображается в диапазон 2–5 секунд. Распределение исходов по популяции остаётся 90/10,
   ожидание выполняется только через порт `Clock`.
3. **Получатель webhook обязан дедуплицировать** по `event_id`. Это часть публичного
   контракта и должно быть написано в README.
4. **Публикация в брокер подтверждается.** Событие помечается опубликованным только после
   подтверждения от брокера, а не после записи в сокет. Иначе outbox не даёт никакой
   гарантии: потерянное сообщение будет считаться доставленным.

## 3. Инварианты Payment

**Состояния:** `pending`, `succeeded`, `failed`. Других состояний нет.

**Допустимые переходы — только два:**

```
pending → succeeded
pending → failed
```

Любой другой переход, включая повторный переход в тот же терминальный статус, — ошибка
домена, а не молчаливый no-op.

**Терминальность.** `succeeded` и `failed` терминальны. Попытка обработать уже терминальный
платёж не является ошибкой на уровне сообщения — это штатный сценарий повторной доставки,
и обработчик до доменного перехода в этом случае не доходит.

**Обращение к шлюзу.** Инвариант: **не более одного одновременного обращения** к платёжному
шлюзу на платёж. Абсолютного «ровно один раз» гарантировать нельзя — процесс может умереть
между вызовом шлюза и записью результата. Безопасность повтора обеспечивается двумя
свойствами: исход детерминирован по `payment_id` (§2.2), поэтому повтор не может дать другой
ответ; запись результата разрешена только из состояния `pending`, поэтому терминальный статус
не будет перезаписан.

**Захват в работу** — не четвёртое состояние, а метка времени на строке платежа. Захват
выполняется одной атомарной операцией вместе с проверкой `status = pending`, а не чтением
с последующей записью. Срок удержания — **30 секунд**: верхняя граница работы шлюза (5 с)
плюс запас на запись результата и остановку процесса. По истечении срока захват может быть
взят повторно, иначе смерть процесса подвесила бы платёж навсегда.

**Инварианты полей.** `amount > 0`. `currency ∈ {RUB, USD, EUR}`. `processed_at` заполнен
тогда и только тогда, когда статус терминален. `idempotency_key` уникален.

## 4. Порты (швы)

Всё недетерминированное и внешнее вынесено за интерфейс. Реализации живут в инфраструктуре,
в тестах подменяются фейками с явным поведением.

| Порт | Ответственность | Фейки в тестах |
|---|---|---|
| `PaymentGateway` | Проведение платежа. Продуктовая реализация: исход и длительность детерминированы по `payment_id`, 90/10, 2–5 секунд | `AlwaysSucceeds`, `AlwaysFails`, `FailsThenSucceeds(n)` |
| `WebhookSender` | Доставка уведомления по HTTP | Фейк с программируемой последовательностью ответов и счётчиком обращений |
| `Clock` | Текущее время и ожидание | Фиксированное время, ожидание без реальной задержки |
| `IdGenerator` | Идентификаторы платежей и событий | Детерминированная последовательность |

Следствия, которые легко нарушить незаметно:

- Идентификаторы **не** генерируются на стороне БД, иначе `IdGenerator` становится фикцией.
- Временные метки **не** проставляются значением по умолчанию на стороне БД, иначе `Clock`
  становится фикцией и `processed_at` невозможно проверить точным сравнением.
- Задержки разделены на чистые функции, возвращающие число секунд, и собственно ожидание
  через `Clock`. Тестируются функции.

## 5. Outbox

### 5.1. Транзакционная граница

**Одна транзакция:** запись платежа и запись события в outbox. Один коммит. При откате не
остаётся ни платежа, ни события.

**Публикация в брокер вынесена из HTTP-пути полностью.** Публикация прямо в обработчике
запроса делает outbox бессмысленным: если брокер недоступен, запрос упадёт, а весь смысл
паттерна в том, чтобы он не упал.

### 5.2. Relay

Relay — отдельный **компонент** (собственный модуль, собственный сценарий, собственные
тесты), но **не отдельный процесс и не отдельный сервис**. Запускается фоновой задачей в
процессе consumer'а при старте и останавливается вместе с ним.

Помещён в consumer, а не в api, по одной причине: relay удерживает блокировки строк на всё
время публикации и занимает соединения из того же пула. В процессе api при зависшем брокере
это деградация HTTP — ровно то, что outbox должен предотвращать. Consumer же и так фоновый
воркер.

**Порядок операций строгий:** выборка неопубликованных событий с блокировкой, пропускающей
занятые другими строки → публикация → **ожидание подтверждения от брокера** → пометка
события опубликованным. Обратный порядок (пометка до подтверждения) теряет события; принятый
порядок допускает дубли, что покрыто идемпотентностью consumer'а из §2.

Размер выборки — 50 событий. Больше нельзя: блокировки удерживаются всё время публикации,
и длинная транзакция мешает обслуживанию таблицы.

### 5.3. Хранение

Строка outbox хранит счётчик попыток, время следующей попытки и текст последней ошибки.
Без времени следующей попытки одно неопубликуемое событие даёт бесконечный горячий цикл;
без счётчика и текста ошибки причину невозможно диагностировать.

**Опубликованные строки не удаляются** — они служат журналом для расследований. Выборка идёт
по частичному индексу, покрывающему только неопубликованные, поэтому рост таблицы не
замедляет relay. Периодическая чистка старых записей за границами задания и отмечается в
README как известное ограничение.

## 6. Три разных retry

Механизмы разные, путать их нельзя. Все три задержки — независимые константы с разными
именами; совпадение чисел между ними не подразумевается.

### 6.1. Retry публикации из outbox

Кто: relay. Когда: брокер недоступен или не подтвердил публикацию.

Событие остаётся неопубликованным, время следующей попытки сдвигается с ростом задержки,
потолок задержки — 60 секунд. Верхней границы числа попыток нет: событие не теряется.
После **10** неудач подряд событие дополнительно логируется на уровне ошибки как требующее
внимания, но попытки продолжаются.

### 6.2. Retry отправки webhook

Кто: обработчик.

**На первом прогоне обработчика — 3 попытки** с задержками `webhook_backoff`: 1 секунда
перед второй попыткой, 2 секунды перед третьей. Первичная отправка плюс 2 повтора = 3
обращения.

**На повторных прогонах (§6.3) — одна попытка.** Три полных цикла на каждом прогоне
избыточны: брокерный retry сам по себе является отложенным повтором доставки и уже несёт
экспоненциальную задержку. Итого не более 3 + 1 + 1 + 1 = **6 обращений** к получателю на
платёж вместо 12.

Повторяем при: сетевой ошибке, таймауте, ответе `5xx`, а также `408` и `429`. Для `429`
учитывается `Retry-After`, но не более **30 секунд** — иначе получатель может подвесить
нашего обработчика на произвольное время и сорвать подтверждение сообщения по таймауту.

**Не** повторяем при остальных `4xx`: получатель осознанно отверг payload, повтор ничего не
изменит.

Исчерпание попыток трактуется как временный отказ обработки и уводит сообщение в §6.3.

### 6.3. Retry обработки сообщения и DLQ

Кто: брокер. Сколько: **3 повтора** с задержками 2 / 4 / 8 секунд, после чего сообщение
уходит в Dead Letter Queue.

Семантика счёта фиксируется явно: первичная обработка + 3 повтора = **4 прогона
обработчика**, после неуспеха четвёртого сообщение в DLQ.

**Носитель счётчика — собственный заголовок сообщения `x-attempt`.** Штатные сведения о
dead-letter для этого непригодны: они агрегируются по паре «очередь + причина», а при
отдельной очереди на каждую попытку (§7) счёт в каждой из них равен единице. Отсутствие
заголовка трактуется как ноль. Публикующая сторона инкрементирует его при каждом уходе в
retry; заголовок сохраняется при dead-letter и доезжает до DLQ.

**Классификация отказов.**

| Класс | Примеры | Действие |
|---|---|---|
| Временный | БД недоступна, брокер недоступен, webhook не доставлен после §6.2 | Уход в retry-очередь |
| Постоянный | Тело сообщения не разбирается, неизвестный тип события, платёж не найден | Немедленно в DLQ, минуя повторы |

**Правило по умолчанию: любое неклассифицированное исключение считается временным.** Список
постоянных отказов закрытый и перечислен выше. Повторять заведомо безнадёжное бессмысленно,
но и терять сообщение из-за неучтённой ошибки нельзя, поэтому умолчание — в пользу повтора.

**Что НЕ является отказом обработки:** платёж со статусом `failed`. Это успешно обработанное
сообщение с отрицательным бизнес-результатом. Статус записан, webhook отправлен, сообщение
подтверждено. В DLQ такое сообщение не попадает никогда.

## 7. Топология брокера

```
exchange payments (direct, durable)
 ├─ payments.new            rk = payments.new
 │     dead-letter → payments.dlx / payments.new.dlq     (только страховочная сетка)
 ├─ payments.new.retry.1    ttl 2s  → payments / payments.new
 ├─ payments.new.retry.2    ttl 4s  → payments / payments.new
 └─ payments.new.retry.3    ttl 8s  → payments / payments.new

exchange payments.dlx (direct, durable)
 └─ payments.new.dlq        без ttl, без dead-letter
```

### 7.1. Как сообщение попадает в retry и в DLQ

Маршрутизацию выполняет **сам обработчик явной публикацией**, а не отклонением сообщения.

| Исход прогона | Действие обработчика |
|---|---|
| Успех | подтвердить сообщение |
| Временный отказ, `x-attempt < 3` | опубликовать в `payments.new.retry.{x-attempt + 1}` с инкрементированным заголовком → дождаться подтверждения от брокера → подтвердить исходное сообщение |
| Временный отказ, `x-attempt = 3` | опубликовать в `payments.dlx` с ключом `payments.new.dlq` → дождаться подтверждения → подтвердить исходное |
| Постоянный отказ | опубликовать в DLQ немедленно → подтвердить исходное |
| Публикация не удалась | **не подтверждать**, вернуть сообщение брокеру |

Dead-letter, объявленный у самой `payments.new`, в штатном потоке не участвует — это
страховка на случай исключения, не перехваченного обработчиком, чтобы такое сообщение попало
в DLQ, а не исчезло.

**Порядок «публикация → подтверждение брокера → подтверждение исходного сообщения» обязателен
и не может быть переставлен.** Обратный порядок теряет сообщение при смерти процесса между
операциями.

### 7.2. Решения, каждое из которых при нарушении ломает цепочку молча

- **Отдельная очередь на каждую попытку**, а не срок жизни, назначаемый отдельному сообщению.
  Причина первая: при сроке жизни на сообщение брокер проверяет истечение только у головы
  очереди, и сообщение с задержкой 8 секунд задержит стоящее за ним с задержкой 2 секунды.
  Причина вторая: сведения о dead-letter агрегируются по паре «очередь + причина», и детектор
  циклов брокера уничтожает сообщение, если за весь цикл не было ни одного явного отклонения;
  разные очереди на попытку от этого защищают.
- **Ключ маршрутизации при dead-letter задаётся явно.** По умолчанию брокер сохраняет
  исходный ключ сообщения — то есть имя retry-очереди, для которого связки не существует.
  Сообщение стало бы немаршрутизируемым и было бы уничтожено без единой записи в логе.
- **Retry-очереди и DLQ объявляются явно при старте.** У них нет подписчиков, поэтому
  фреймворк их не создаст, а публикация в несуществующую очередь теряется молча.
- **Все обменники и очереди durable, все сообщения persistent.** Подтверждение публикации
  без persistent означает лишь «брокер принял в память» и не переживает его перезапуск.
- **Ограничение на число неподтверждённых сообщений у consumer'а задаётся явно** (10). При
  обработке 2–5 секунд и снятом ограничении consumer выберет всю очередь, и брокер разорвёт
  канал по таймауту подтверждения, вернув все сообщения обратно — цикл, который не сходится.

### 7.3. Содержимое сообщения в DLQ

Сообщение сохраняет исходное тело и заголовки, к которым добавляются: причина отказа, класс
отказа (временный или постоянный), `payment_id` и номер прогона. Без этого разбор DLQ
превращается в угадайку.

## 8. Контракты API

Все эндпоинты требуют заголовок `X-API-Key`. Сравнение ключа — постоянное по времени.

### 8.1. Представление платежа

Единое для ответов обоих эндпоинтов: `id`, `amount`, `currency`, `description`, `metadata`,
`status`, `webhook_url`, `created_at`, `processed_at`.

**Сумма во всех исходящих представлениях — строка** с фиксированным масштабом (`"100.00"`),
одинаково в ответах API, в событии и в webhook. Хранение — точный десятичный тип с масштабом
4 и разрядностью 20. Число с плавающей точкой для денег недопустимо ни на одном участке.
`processed_at` равен `null`, пока статус не терминален.

### 8.2. `POST /api/v1/payments`

Заголовки: `X-API-Key` (обязательный), `Idempotency-Key` (обязательный).

Тело: `amount`, `currency`, `description`, `metadata`, `webhook_url`.
`description` и `metadata` необязательны. **`webhook_url` необязателен** — задание не
называет его обязательным, и отвергать корректный запрос из-за нашего удобства неправильно.
Платёж без `webhook_url` обрабатывается штатно и считается уведомлённым без отправки.

| Ситуация | Код | Тело |
|---|---|---|
| Создан | `202` | `payment_id`, `status = pending`, `created_at` |
| Тот же ключ, то же тело | `202` | исходный платёж с его **фактическим текущим статусом**, новое событие в outbox не создаётся |
| Тот же ключ, другое тело | `409` | описание конфликта |
| Нет `X-API-Key` или неверный | `401` | |
| Нет `Idempotency-Key` | `422` | |
| Невалидное тело | `422` | |

### 8.3. Идемпотентность

Совпадение тела определяется хешем канонической формы запроса: ключи отсортированы, сумма
приведена к строке с фиксированным масштабом. Без канонизации клиент, честно повторяющий тот
же запрос, получил бы `409` из-за порядка ключей в метаданных или записи `100` против `100.00`.

**Хеш хранится в строке платежа** рядом с `idempotency_key` — иначе при повторе не с чем
сравнивать.

Гонка двух одновременных запросов с одним ключом разрешается вставкой, не порождающей ошибку
при конфликте: при конфликте вставка возвращает пустой результат, платёж перечитывается по
ключу в той же транзакции, хеши сравниваются. Перехват нарушения уникальности с последующим
перечитыванием непригоден: в PostgreSQL транзакция после ошибки переходит в состояние отката
и любой следующий запрос в ней завершится ошибкой. В ветке конфликта событие в outbox не
создаётся.

### 8.4. `GET /api/v1/payments/{payment_id}`

| Ситуация | Код |
|---|---|
| Найден | `200`, представление из §8.1 |
| Не найден | `404` |
| Нет `X-API-Key` или неверный | `401` |

Формат ошибок единый для всех кодов.

## 9. Контракты события и webhook

**Событие в очереди** содержит идентификатор события (он же ключ дедупликации), тип,
`payment_id` и данные, достаточные для обработки.

**Webhook** содержит: `event_id`, тип события, `payment_id`, финальный статус, сумму, валюту,
`processed_at`. Наличие `event_id` обязательно — без него получатель не может выполнить
дедупликацию, которую мы от него требуем в §2.

**Повторная отправка.** Инвариант «повторная доставка не шлёт второй webhook» уточняется:
второй webhook не отправляется, **если предыдущий был доставлен успешно**. Факт доставки
хранится отдельно от статуса платежа. Иначе платёж, чей webhook не удалось доставить,
никогда не получил бы уведомления, и механизм §6.3 оказался бы бесполезен.

Поведение обработчика при получении события:

| Состояние платежа | Действие |
|---|---|
| `pending` | захват → шлюз → статус → webhook |
| терминальный, `webhook_url` отсутствует | подтвердить сообщение, ничего не делать |
| терминальный, webhook доставлен | подтвердить сообщение, ничего не делать |
| терминальный, webhook не доставлен | только повторить webhook (одна попытка, §6.2) |

## 10. Безопасность и лимиты

- `X-API-Key` — статический ключ из конфигурации, сравнение постоянное по времени.
- `webhook_url` задаётся клиентом, то есть сервис по внешнему запросу отправляет POST на
  произвольный адрес. В рамках задания ограничиваемся запретом переадресаций, таймаутом
  5 секунд и лимитом на размер ответа. Полноценный список разрешённых адресов и защита от
  подмены DNS — за границей задания, отмечается в README как известное ограничение.
- `description` — не более 512 символов.
- `metadata` — объект верхнего уровня, не более 8 КБ в сериализованном виде.

## 11. Состав окружения

**Ровно четыре сервиса, как перечислено в задании:** `postgres`, `rabbitmq`, `api`,
`consumer`. Ничего сверх этого списка.

- **relay** — фоновая задача внутри процесса `consumer` (§5.2), отдельной строки в compose
  не имеет.
- **Миграции** применяются командой запуска `api` перед стартом веб-сервера. Отдельный
  однократный сервис был бы чище при нескольких репликах, но реплика одна, гонки за версию
  схемы нет, а список сервисов задан заданием.
- **Приёмник webhook** в окружение не входит. Для сквозного теста поднимается эхо-сервер
  внутри самого теста. Для ручной демонстрации попадания в DLQ приёмник не нужен вовсе:
  достаточно указать недостижимый `webhook_url`, и цепочка §6.2 → §6.3 отработает
  по-настоящему. Для демонстрации успешной доставки README предлагает внешний публичный
  приёмник.

Тесты, которым нужна БД или брокер, поднимают контейнер сами — один на сессию. Если во
внешней конфигурации задан адрес готового экземпляра, используется он: так те же тесты
работают и локально, и в CI поверх сервисных контейнеров.

## 12. Решения, принятые по умолчанию

Приняты в отсутствие возражений, каждое отменяемо на этапе согласования RFC.

1. `webhook_url` необязателен; платёж без него считается уведомлённым (§8.2).
2. Число обращений webhook: 3 на первом прогоне, по одному на повторных (§6.2).
3. Задержки: `webhook_backoff` = 1 / 2 секунды, TTL retry-очередей = 2 / 4 / 8 секунд.
   Это разные константы, совпадение не подразумевается.
4. Срок удержания захвата — 30 секунд (§3).
5. «3 попытки» из задания читаются как «3 повторных прогона», итого 4 прогона обработчика.
6. Отсутствие `Idempotency-Key` даёт `422`, а не `400`: заголовок описан как часть схемы
   запроса и обрабатывается общей валидацией.
7. `idempotency_key` уникален глобально, срок жизни не ограничен. При единственном статическом
   API-ключе разделение по клиентам смысла не имеет.
8. Опубликованные строки outbox не удаляются (§5.3).
9. Ограничение неподтверждённых сообщений у consumer'а — 10 (§7.2).

## 13. Отвергнутые альтернативы

| Альтернатива | Причина отказа |
|---|---|
| Relay отдельным процессом или сервисом в compose | Задание задаёт состав окружения из четырёх сервисов. Разделение процессов дало бы независимое масштабирование, но при одной реплике выигрыша нет, а список сервисов разошёлся бы с заданием |
| Relay внутри процесса `api` | Удерживает блокировки строк и соединения пула на время публикации; при зависшем брокере деградирует HTTP — ровно то, что outbox предотвращает |
| Публикация в брокер прямо в обработчике HTTP-запроса | Обесценивает outbox: недоступность брокера роняет приём платежа. Публикация после коммита «по возможности» тоже не спасает — падение между коммитом и публикацией теряет событие навсегда |
| Отдельный сервис-приёмник webhook в compose | Инфраструктура сверх заданного состава. Для DLQ достаточно недостижимого адреса, для сквозного теста — эхо-сервера внутри теста |
| Отдельный однократный сервис миграций | То же: сверх заданного состава. Оправдан при нескольких репликах api, которых здесь нет |
| Маршрутизация в retry отклонением сообщения вместо публикации | Отклонение уводит сообщение по dead-letter самой очереди, то есть сразу в DLQ, минуя все задержки |
| Счёт попыток по штатным сведениям о dead-letter | Агрегируются по паре «очередь + причина»; при очереди на попытку счёт в каждой равен единице (§6.3) |
| Плагин отложенных сообщений вместо цепочки retry-очередей | Требует нестандартного образа брокера, привязан к его версии, хранит отложенные сообщения без репликации. Слабее демонстрирует работу с обменниками и dead-letter |
| Встроенный в FastStream параметр `retry` | Выполнял отклонение с немедленным возвратом в очередь, без задержки; в версии 0.6 объявлен устаревшим, в 0.7 удалён |
| Один срок жизни на сообщение вместо очереди на попытку | Блокировка головой очереди и риск уничтожения детектором циклов (§7.2) |
| Перехват нарушения уникальности с перечитыванием в той же транзакции | В PostgreSQL транзакция после ошибки непригодна к использованию (§8.3) |
| Отдельная очередь для доставки webhook | Разводит домены отказа и убирает попадание успешного платежа в DLQ, но добавляет вторую цепочку очередей при объёме задания, где хватает одной. Отмечается в README как продуктовое улучшение |
| `random()` в момент обработки | Даёт противоречащие результаты при повторной доставке дубля (§2.2) |
| Генерация идентификаторов и времени на стороне БД | Обесценивает порты `Clock` и `IdGenerator` (§4) |
| Нативный перечислимый тип PostgreSQL для статуса | Изменение набора значений требует ручных операций в миграциях и не подхватывается автогенерацией. Взамен — строка с ограничением на допустимые значения на уровне БД плюс перечисление в домене |
| Удаление строк outbox после публикации | Теряется журнал для расследований, а выигрыш отсутствует: выборка идёт по частичному индексу и от размера таблицы не зависит |
