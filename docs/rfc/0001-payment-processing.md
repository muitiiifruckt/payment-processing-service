# RFC 0001. Асинхронный процессинг платежей

**Статус:** на согласовании
**Дата:** 2026-08-14

Документ фиксирует решения, границы и контракты до написания кода. После согласования
не переписывается — изменения идут через ADR в `docs/adr/`.

---

## 1. Контекст и цель

Сервис принимает запросы на оплату, ставит их в очередь, обрабатывает через эмуляцию
внешнего платёжного шлюза и уведомляет клиента о результате через webhook.

Синхронная часть (HTTP) обязана быть быстрой и не зависеть от доступности брокера:
приём платежа считается состоявшимся в момент коммита в БД, а не в момент публикации
события.

---

## 2. Гарантия доставки

**Принимаем at-least-once на всех трёх участках:** outbox → брокер, брокер → consumer,
consumer → webhook получателя.

Exactly-once недостижим: между вызовом внешнего шлюза и записью результата в БД всегда
существует окно, в котором процесс может умереть. Мы не пытаемся его закрыть, мы делаем
повтор безопасным.

Прямые следствия, обязательные к реализации:

1. **Consumer идемпотентен.** Повторная доставка того же события не приводит к повторному
   обращению к шлюзу и не меняет уже терминальный статус.
2. **Эмуляция шлюза детерминирована по `payment_id`.** Исход вычисляется как функция от
   идентификатора, а не через `random()` в момент вызова. Иначе две параллельные обработки
   дубля могут дать противоречащие результаты, и клиент получит два взаимоисключающих
   уведомления. Распределение по популяции остаётся 90/10.
3. **Получатель webhook обязан дедуплицировать** по `event_id`. Это часть публичного
   контракта и должно быть написано в README.
4. **Публикация в брокер подтверждается.** Событие помечается опубликованным только после
   подтверждения от брокера (publisher confirms), а не после записи в сокет. Иначе outbox
   не даёт никакой гарантии — потерянное сообщение будет считаться доставленным.

---

## 3. Инварианты Payment

**Состояния:** `pending`, `succeeded`, `failed`.

**Допустимые переходы — только два:**

```
pending → succeeded
pending → failed
```

Любой другой переход — ошибка домена (`InvalidTransition`), а не молчаливый no-op.

**Терминальность.** `succeeded` и `failed` терминальны. Из терминального состояния переходов
нет. Попытка обработать уже терминальный платёж не является ошибкой на уровне сообщения —
это штатный сценарий повторной доставки.

**Запрет повторной обработки.** Обращение к платёжному шлюзу допустимо ровно один раз на
платёж. Гарантируется атомарным захватом (claim) строки платежа перед вызовом шлюза:
переход в «взято в работу» и проверка `status = pending` выполняются одной операцией, а не
как чтение с последующей записью. У захвата есть срок протухания, иначе смерть процесса
между захватом и записью результата навсегда подвесит платёж.

**Инварианты полей.** `amount > 0`. `currency ∈ {RUB, USD, EUR}`. `processed_at` заполнен
тогда и только тогда, когда статус терминален. `idempotency_key` уникален.

## 4. Порты (швы)

Всё недетерминированное и внешнее вынесено за интерфейс. Реализации живут в инфраструктуре,
в тестах подменяются фейками с явным поведением.

| Порт | Ответственность | Фейки в тестах |
|---|---|---|
| `PaymentGateway` | Проведение платежа. Продуктовая реализация: задержка 2–5 сек, исход 90/10, детерминирован по `payment_id` | `AlwaysSucceeds`, `AlwaysFails`, `FailsThenSucceeds(n)` |
| `WebhookSender` | Доставка уведомления по HTTP | Фейк с программируемой последовательностью ответов и счётчиком попыток |
| `Clock` | Текущее время и задержка (`now`, `sleep`) | Фиксированное время, задержка без реального ожидания |
| `IdGenerator` | Идентификаторы платежей и событий | Детерминированная последовательность |

Следствия, которые легко нарушить незаметно:

- Идентификаторы **не** генерируются на стороне БД (`gen_random_uuid()`), иначе `IdGenerator`
  становится фикцией.
- Временные метки **не** проставляются через `server_default=now()`, иначе `Clock` становится
  фикцией и `processed_at` невозможно проверить точным сравнением.
- Задержка между повторами webhook разделена на две части: чистая функция `backoff(attempt)`,
  возвращающая число секунд, и собственно ожидание через `Clock`. Тестируется первая.

## 5. Транзакционная граница outbox

**Одна транзакция:** запись платежа и запись события в outbox. Один коммит. При откате не
остаётся ни платежа, ни события.

**Публикация в брокер вынесена из HTTP-пути полностью.** Публикует отдельный процесс-relay,
читающий неопубликованные события. Публикация прямо в обработчике запроса делает outbox
бессмысленным: если брокер недоступен, запрос упадёт, а весь смысл паттерна в том, чтобы
он не упал.

**Порядок операций в relay строгий:** выборка неопубликованных событий с блокировкой,
пропускающей уже занятые строки → публикация → **ожидание подтверждения от брокера** →
пометка события опубликованным. Обратный порядок (пометка до подтверждения) теряет события;
принятый порядок допускает дубли, что покрыто идемпотентностью consumer'а из §2.

**Строка outbox хранит** счётчик попыток, время следующей попытки и текст последней ошибки.
Без времени следующей попытки одно неопубликуемое событие даёт бесконечный горячий цикл;
без счётчика и текста ошибки причину невозможно диагностировать.

## 6. Три разных retry

Механизмы разные, путать их нельзя.

### 6.1. Retry публикации из outbox

Кто: relay. Когда: брокер недоступен или не подтвердил публикацию.
Событие остаётся неопубликованным, время следующей попытки сдвигается с ростом задержки.
Верхней границы попыток нет — событие не теряется, но после порога помечается как требующее
внимания и логируется на уровне ошибки.

### 6.2. Retry отправки webhook

Кто: обработчик. Сколько: **3 попытки** с экспоненциальной задержкой.

Повторяем при: сетевой ошибке, таймауте, ответе `5xx`, а также `408` и `429` (для `429`
учитывается `Retry-After`).
**Не** повторяем при остальных `4xx` — получатель осознанно отверг payload, повтор ничего
не изменит.

Исчерпание попыток трактуется как временный отказ обработки и уводит сообщение в §6.3.

### 6.3. Retry обработки сообщения и DLQ

Кто: брокер. Сколько: **3 повтора** с задержками 2 / 4 / 8 секунд, после чего сообщение
уходит в Dead Letter Queue.

Семантика счёта фиксируется явно: первичная обработка + 3 повтора = **4 прогона обработчика**,
после неуспеха четвёртого сообщение в DLQ. Формулировка задания «не обработанных после
3 попыток» читается как «после 3 повторных попыток».

**Что уводит сообщение в retry:** временные отказы — БД недоступна, брокер недоступен,
webhook не доставлен после §6.2.

**Что уводит сообщение в DLQ немедленно, минуя повторы:** постоянные отказы — тело
сообщения не разбирается, неизвестный тип события, неизвестная валюта. Повторять разбор
заведомо бессмысленно.

**Что НЕ является отказом обработки:** платёж со статусом `failed`. Это успешно обработанное
сообщение с отрицательным бизнес-результатом. Статус записан, webhook отправлен, сообщение
подтверждено. В DLQ такое сообщение не попадает никогда.

## 7. Топология брокера

```
exchange payments (direct, durable)
 ├─ payments.new            rk = payments.new
 │     dead-letter → payments.dlx / payments.new.dlq        (страховочная сетка)
 ├─ payments.new.retry.1    ttl 2s  → payments / payments.new
 ├─ payments.new.retry.2    ttl 4s  → payments / payments.new
 └─ payments.new.retry.3    ttl 8s  → payments / payments.new

exchange payments.dlx (direct, durable)
 └─ payments.new.dlq        без ttl, без dead-letter
```

Решения, каждое из которых при нарушении ломает цепочку молча:

- **Отдельная очередь на каждую попытку**, а не срок жизни, назначаемый отдельному сообщению.
  Причина первая: при сроке жизни на сообщение брокер проверяет истечение только у головы
  очереди, и сообщение с задержкой 8 секунд задержит стоящее за ним с задержкой 2 секунды.
  Причина вторая: сведения о dead-letter агрегируются по паре «очередь + причина», и
  детектор циклов брокера уничтожает сообщение, если за весь цикл не было ни одного явного
  отклонения; разные очереди на попытку от этого защищают.
- **Ключ маршрутизации при dead-letter задаётся явно.** По умолчанию брокер сохраняет
  исходный ключ сообщения — то есть имя retry-очереди, для которого связки не существует.
  Сообщение стало бы немаршрутизируемым и было бы уничтожено без единой записи в логе.
- **Retry-очереди и DLQ объявляются явно при старте.** У них нет подписчиков, поэтому
  фреймворк их не создаст, а публикация в несуществующую очередь теряется молча.
- **Все обменники и очереди durable, все сообщения persistent.** Подтверждение публикации
  без persistent означает лишь «брокер принял в память» и не переживает его перезапуск.
- **Ограничение на число неподтверждённых сообщений у consumer'а задаётся явно.** При
  обработке 2–5 секунд и снятом ограничении consumer выберет всю очередь, и брокер разорвёт
  канал по таймауту подтверждения, вернув все сообщения обратно — цикл, который не сходится.

## 8. Контракты API

Все эндпоинты требуют заголовок `X-API-Key`. Сравнение ключа — постоянное по времени.

### `POST /api/v1/payments`

Заголовки: `X-API-Key` (обязательный), `Idempotency-Key` (обязательный).
Тело: сумма, валюта, описание, метаданные, `webhook_url`.

| Ситуация | Код | Тело |
|---|---|---|
| Создан | `202` | `payment_id`, `status = pending`, `created_at` |
| Тот же ключ, то же тело | `202` | исходный платёж, новое событие в outbox **не создаётся** |
| Тот же ключ, другое тело | `409` | описание конфликта |
| Нет `X-API-Key` или неверный | `401` | |
| Нет `Idempotency-Key` | `422` | |
| Невалидное тело (валюта, сумма ≤ 0, `webhook_url`) | `422` | |

Совпадение тела определяется хешем канонической формы запроса: ключи отсортированы, сумма
приведена к строке с фиксированной точностью. Без канонизации клиент, честно повторяющий
тот же запрос, получил бы `409` из-за порядка ключей в метаданных.

Гонка двух одновременных запросов с одним ключом разрешается на уровне БД вставкой,
не создающей конфликта, а не перехватом исключения с последующим перечитыванием: в
PostgreSQL после ошибки транзакция переходит в состояние отката, и повторное чтение в ней
невозможно.

### `GET /api/v1/payments/{payment_id}`

| Ситуация | Код |
|---|---|
| Найден | `200`, полное представление платежа |
| Не найден | `404` |
| Нет `X-API-Key` | `401` |

Формат ошибок единый для всех кодов.

## 9. Контракты события и webhook

**Событие в очереди** содержит идентификатор события (он же ключ дедупликации), тип,
идентификатор платежа и данные, достаточные для обработки. Сумма сериализуется строкой —
число с плавающей точкой для денег недопустимо.

**Webhook** содержит: `event_id`, тип события, `payment_id`, финальный статус, сумму,
валюту, `processed_at`. Наличие `event_id` обязательно — без него получатель не может
выполнить дедупликацию, которую мы от него требуем в §2.

**Повторная отправка webhook.** Инвариант «повторная доставка не шлёт второй webhook»
уточняется: второй webhook не отправляется, **если предыдущий был доставлен успешно**.
Факт доставки хранится отдельно от статуса платежа. Иначе платёж, чей webhook не удалось
доставить, никогда не получил бы уведомления, и весь механизм §6.3 оказался бы бесполезен.

Поведение обработчика при повторной доставке события:

| Состояние платежа | Действие |
|---|---|
| `pending` | захват → шлюз → статус → webhook |
| терминальный, webhook доставлен | подтвердить сообщение, ничего не делать |
| терминальный, webhook не доставлен | только повторить webhook |

## 10. Безопасность

- `X-API-Key` — статический ключ из конфигурации, сравнение постоянное по времени.
- `webhook_url` задаётся клиентом, то есть сервис по внешнему запросу отправляет POST на
  произвольный адрес. В рамках задания ограничиваемся запретом переадресаций, жёстким
  таймаутом и лимитом на размер ответа. Полноценный список разрешённых адресов и защита от
  подмены DNS — за границей задания, отмечается в README как известное ограничение.
- Размер метаданных ограничен.

## 11. Решения, принятые по умолчанию

Приняты в отсутствие возражений, каждое отменяемо на этапе согласования RFC.

1. Факт доставки webhook хранится отдельным полем (§9).
2. Число попыток webhook остаётся 3, несмотря на перемножение с §6.3 — до 12 обращений к
   получателю в худшем случае. Цифра взята из задания; расхождение объясняется в README.
3. Приёмник webhook для демонстрации — отдельный минимальный сервис в compose, а не эндпоинт
   в продуктовом приложении. Поддерживает управляемый отказ, чтобы падение в DLQ можно было
   воспроизвести одной командой.
4. Тесты, которым нужна БД, поднимают контейнер сами — один на сессию.

## 12. Отвергнутые альтернативы

| Альтернатива | Причина отказа |
|---|---|
| Плагин отложенных сообщений вместо цепочки retry-очередей | Требует нестандартного образа брокера, привязан к его версии, хранит отложенные сообщения без репликации. Слабее демонстрирует работу с обменниками и dead-letter |
| Встроенный в фреймворк параметр повторов | Отклонение без задержки; в актуальной версии удалён |
| Один срок жизни на сообщение вместо очереди на попытку | Блокировка головой очереди и риск уничтожения детектором циклов (§7) |
| Публикация в брокер прямо в обработчике HTTP-запроса | Обесценивает outbox: недоступность брокера роняет приём платежа |
| Перехват нарушения уникальности с перечитыванием в той же транзакции | В PostgreSQL транзакция после ошибки непригодна к использованию (§8) |
| Отдельная очередь для доставки webhook | Чище по разделению доменов отказа, но противоречит требованию «один consumer, делающий всё». Отмечается в README как продуктовое улучшение |
| `random()` в момент обработки | Даёт противоречащие результаты при повторной доставке дубля (§2) |
| Генерация идентификаторов и времени на стороне БД | Обесценивает порты `Clock` и `IdGenerator` (§4) |
| Нативный перечислимый тип PostgreSQL для статуса | Не отслеживается автогенерацией миграций, требует ручных операций при изменении |
| Прогон миграций в команде запуска каждого сервиса | Гонка нескольких процессов за версию схемы. Отдельный однократный шаг |
