# Список тестов

**Статус:** на согласовании. После согласования замораживается и служит критерием готовности.
Добавление пункта по ходу работы — отдельным коммитом с пояснением.

Сценарии сформулированы на языке домена. Группировка по слайсам совпадает с RFC 0001.
Пометки: `[u]` unit — без I/O, `[i]` integration — реальные Postgres / RabbitMQ / HTTP,
`[e]` e2e — поднятое окружение целиком.

---

## Слайс 1. Домен

- `[u]` новый платёж создаётся в статусе `pending`, `processed_at` пуст
- `[u]` переход `pending → succeeded` проставляет `processed_at` из `Clock`
- `[u]` переход `pending → failed` проставляет `processed_at` из `Clock`
- `[u]` переход из терминального статуса запрещён и поднимает ошибку домена
- `[u]` повторный переход в тот же терминальный статус запрещён
- `[u]` сумма, равная нулю или отрицательная, отвергается
- `[u]` валюта вне множества `{RUB, USD, EUR}` отвергается
- `[u]` сумма сохраняет масштаб: `100` и `100.00` дают одно значение
- `[u]` `webhook_backoff(attempt)` возвращает `[1.0, 2.0]` для попыток 1 и 2
- `[u]` задержка retry-очередей задана константами `[2, 4, 8]` и не совпадает с `webhook_backoff`

## Слайс 2. Персистентность и outbox

- `[i]` сохранённый платёж читается обратно без потери суммы и масштаба
- `[i]` при создании платежа в outbox появляется ровно одно событие
- `[i]` платёж и событие пишутся атомарно: при откате нет ни одной строки
- `[i]` второй платёж с тем же `idempotency_key` не создаётся
- `[i]` два одновременных запроса с одним `idempotency_key` дают один платёж и одно событие
- `[i]` захват платежа удаётся один раз; второй захват до истечения срока не проходит
- `[i]` захват проходит повторно после истечения срока удержания
- `[i]` захват освобождается при неуспешном прогоне и сразу доступен снова
- `[i]` захват не проходит для платежа в терминальном статусе
- `[i]` срок удержания захвата меньше суммы задержек всех повторов
- `[i]` выборка неопубликованных событий пропускает строки, занятые другим процессом
- `[i]` выборка не возвращает события, время следующей попытки которых ещё не наступило
- `[i]` миграции накатываются и откатываются

## Слайс 3. API

- `[i]` создание платежа возвращает `202` и краткое представление: `payment_id`, `status`, `created_at`
- `[i]` полное представление содержит все поля контракта, сумма — строка с масштабом 2
- `[i]` сумма с более чем двумя знаками после запятой → `422`, а не округление
- `[i]` `processed_at` равен `null`, пока статус не терминален
- `[i]` проба готовности отвечает без `X-API-Key`
- `[i]` повторный запрос с тем же `Idempotency-Key` и тем же телом возвращает тот же `payment_id`
- `[i]` повторный запрос с тем же ключом не создаёт второе событие в outbox
- `[i]` повтор после завершения обработки возвращает полное представление с терминальным статусом, а не `pending`
- `[i]` тот же ключ с другим телом → `409`
- `[i]` порядок ключей в метаданных не влияет на признание тела совпадающим
- `[i]` записи суммы `100` и `100.00` при одном ключе не дают `409`
- `[i]` запрос без `X-API-Key` → `401`
- `[i]` запрос с неверным `X-API-Key` → `401`
- `[i]` получение платежа без `X-API-Key` → `401`
- `[i]` запрос без `Idempotency-Key` → `422`
- `[i]` невалидная валюта → `422`
- `[i]` сумма ≤ 0 → `422`
- `[i]` невалидный `webhook_url` → `422`
- `[i]` описание сверх лимита → `422`
- `[i]` метаданные сверх лимита → `422`
- `[i]` метаданные не-объект → `422`
- `[i]` платёж без `webhook_url`, без описания и без метаданных создаётся
- `[i]` получение существующего платежа возвращает `200` и полное представление
- `[i]` получение несуществующего платежа → `404`
- `[i]` получение по синтаксически неверному идентификатору → `422`
- `[i]` создание платежа не обращается к брокеру

## Слайс 4. Outbox relay

- `[i]` опубликованное событие помечается опубликованным и повторно не публикуется
- `[i]` если брокер не подтвердил публикацию, событие остаётся неопубликованным
- `[i]` если публикация упала, время следующей попытки сдвигается, счётчик растёт, текст ошибки сохранён
- `[i]` задержка следующей попытки не превышает потолок
- `[i]` недоступность брокера не приводит к потере события: оно уходит после восстановления
- `[i]` перекрывающиеся тики relay не публикуют одно событие дважды
- `[i]` `event_id` не меняется при повторной публикации
- `[i]` публикация идёт в заданный обменник с заданным ключом маршрутизации
- `[i]` зависшая публикация прерывается по таймауту и не удерживает транзакцию
- `[i]` падение задачи relay не остаётся незамеченным: задача перезапускается либо процесс завершается
- `[i]` consumer стартует и остаётся живым при недоступном брокере
- `[i]` relay останавливается вместе с процессом, не оставляя незакрытой транзакции
- `[i]` опубликованные строки outbox сохраняются, а не удаляются

## Слайс 5. Consumer

- `[u]` успешная обработка переводит платёж `pending → succeeded`
- `[u]` неуспешная обработка переводит платёж `pending → failed`
- `[u]` исход эмуляции шлюза детерминирован: два вызова для одного платежа дают один результат
- `[u]` длительность эмуляции детерминирована и лежит в диапазоне 2–5 секунд
- `[u]` на выборке идентификаторов доля успехов соответствует 90 % в пределах допуска
- `[i]` повторная доставка того же события не обращается к шлюзу второй раз
- `[i]` повторная доставка не меняет уже терминальный статус
- `[i]` повторная доставка при доставленном webhook не шлёт webhook второй раз
- `[i]` повторная доставка при недоставленном webhook повторяет только webhook
- `[i]` повторная доставка для платежа без `webhook_url` ничего не делает
- `[i]` платёж со статусом `failed` подтверждается как обработанный и не уходит в DLQ
- `[i]` недоступность шлюза отличается от бизнес-отказа: статус не меняется, сообщение уходит в повтор
- `[i]` транзакция БД не удерживается во время обращения к шлюзу и к webhook
- `[i]` принудительный исход из конфигурации переопределяет вычисленный по идентификатору

## Слайс 6. Webhook и retry

- `[u]` webhook содержит `event_id`, `payment_id`, статус, сумму строкой, валюту и `processed_at`
- `[i]` при отказе webhook на первом прогоне делается 3 попытки с растущей задержкой
- `[i]` успех со второй попытки не приводит к третьей
- `[i]` на повторном прогоне делается одна попытка, а не три
- `[i]` ответ `4xx` не повторяется
- `[i]` ответ `5xx` повторяется
- `[i]` ответы `408` и `429` повторяются
- `[i]` `Retry-After` в пределах потолка соблюдается
- `[i]` `Retry-After` сверх потолка игнорируется
- `[i]` ответ сверх лимита размера не приводит к вычитыванию целиком
- `[i]` ответ `3xx` не приводит к переходу по адресу
- `[i]` таймаут считается временным отказом и учитывается как попытка
- `[i]` успешная доставка фиксируется, и повторная обработка её не дублирует
- `[i]` платёж без `webhook_url` не порождает ни одного обращения
- `[u]` публичный адрес назначения разрешён
- `[u]` адрес внутри периметра отвергается: приватные диапазоны, loopback, link-local, `169.254.169.254`
- `[u]` имя, разрешающееся внутрь периметра, отвергается
- `[u]` хост из списка исключений проходит
- `[u]` неразрешимое имя отвергается
- `[i]` к запрещённому адресу не делается ни одного обращения
- `[i]` отвергнутый получателем webhook уводит сообщение в DLQ, не подтверждаясь молча

## Слайс 7. DLQ

- `[i]` retry-очереди и DLQ существуют сразу после старта, до попадания в них сообщений
- `[i]` временный отказ на первом прогоне кладёт сообщение в retry-очередь первой попытки, а не в DLQ
- `[i]` неудавшийся захват уводит сообщение в повтор, а не в DLQ
- `[i]` сообщение из retry-очереди по истечении задержки возвращается в основную очередь
- `[i]` номер прогона растёт от повтора к повтору и доезжает до DLQ
- `[i]` `event_id` не меняется при уходе в повтор и в DLQ
- `[i]` после неуспеха четвёртого прогона сообщение уходит в DLQ
- `[i]` временный отказ, повторяющийся четыре прогона, не оставляет платёж заблокированным
- `[i]` сообщение с неразбираемым телом уходит в DLQ сразу, минуя повторы
- `[i]` неизвестный тип события уходит в DLQ сразу
- `[i]` событие о несуществующем платеже уходит в DLQ сразу
- `[i]` неклассифицированное исключение считается временным и уходит в retry
- `[i]` неудачная публикация в retry-очередь не подтверждает исходное сообщение
- `[i]` сообщение, опубликованное обработчиком в DLQ, несёт причину отказа, класс отказа, `payment_id` и номер прогона
- `[i]` очереди и сообщения переживают перезапуск брокера

## Слайс 8. Сквозной

- `[e]` платёж, созданный через API, доходит до терминального статуса, и webhook приходит в приёмник окружения
- `[e]` окружение поднимается с нуля и схема БД создаётся автоматически
- `[e]` consumer не обращается к БД раньше, чем применены миграции
- `[e]` платёж, созданный при остановленном брокере, обрабатывается после его запуска
- `[e]` платёж с недостижимым `webhook_url` доходит до DLQ, сохраняя терминальный статус
- `[e]` приёмник, отвечающий отказом заданное число раз, показывает успех после повторов
- `[e]` остановка окружения не обрывает прогон посередине
- `[e]` snapshot OpenAPI совпадает с зафиксированным; приёмник webhook в схему не попадает

## Изменения относительно исходного списка

Пункты ниже уточнены или добавлены; обоснование — в RFC 0001.

| Пункт | Что изменилось | Почему |
|---|---|---|
| «повторная доставка не шлёт webhook второй раз» | Разделён на три: при доставленном webhook — не шлёт, при недоставленном — повторяет, при отсутствующем `webhook_url` — ничего не делает | Иначе платёж с недоставленным webhook не был бы уведомлён никогда, и retry обработки терял бы смысл (RFC §9) |
| «успешная обработка: pending → succeeded, проставлен processed_at» | Разнесён по слайсам: переход и `processed_at` проверяются на доменном уровне, поведение обработчика — в слайсе 5, представление `processed_at` — в слайсе 3 | Разная стоимость запуска: доменная часть проверяется без I/O |
| «после 3 неудач сообщение уходит в DLQ» | Уточнено до «после неуспеха четвёртого прогона» | Семантика счёта зафиксирована в RFC §6.3, формулировка не должна допускать второго прочтения |
| «при отказе webhook 3 попытки» | Уточнено: 3 на первом прогоне, одна на повторных | Три полных цикла на каждом из четырёх прогонов дают 12 обращений к чужому эндпоинту (RFC §6.2) |
| Задержки webhook и retry-очередей | Разведены на две независимые константы с разными значениями | В прежней формулировке одна функция обслуживала оба механизма, что смешивало §6.2 и §6.3 |
| Возврат из retry-очереди в основную; «временный отказ кладёт в retry, а не в DLQ» | Добавлено | Единственные тесты, ловящие незаданный ключ маршрутизации при dead-letter и подмену публикации отклонением, из-за которых цепочка молча уничтожает сообщения или обходит все задержки (RFC §7) |
| Подтверждение публикации в relay | Добавлено | Без проверки outbox не даёт гарантии: потерянное сообщение считается доставленным (RFC §2.4) |
| Неразбираемое тело, неизвестный тип события, неклассифицированное исключение | Добавлено | Валидация происходит до тела обработчика, и такое сообщение обходит механизм повторов; правило по умолчанию задано в RFC §6.3 |
| Два одновременных запроса с одним ключом | Добавлено | Гонка на уникальном ключе — типовой сценарий проверки (RFC §8.3) |
| Захват платежа: срок удержания, терминальный статус | Добавлено | Захват введён в RFC §3 как способ не обратиться к шлюзу дважды |
| Детерминизм и распределение эмуляции | Добавлено | `random` без порта запрещён, а детерминизм исхода — предпосылка безопасности повтора (RFC §2.2) |
| Лимиты описания и метаданных, отсутствующий `webhook_url` | Добавлено | Числа заданы в RFC §10, необязательность — в §8.2 |
| Состав представления платежа, сумма строкой | Добавлено | Контракт зафиксирован в RFC §8.1; расхождение сериализации суммы между API и событием — типовая ошибка на деньгах |
| Проверка `X-API-Key` на получении платежа | Добавлено | Задание требует ключ на всех эндпоинтах, в исходном списке проверялось только создание |
| Освобождение захвата, недоступность шлюза, «захват не удался» | Добавлено | Захват, удерживаемый дольше суммы задержек повторов, уводил бы живой платёж в DLQ и оставлял его `pending` навсегда (RFC §3) |
| Живучесть relay и старт при недоступном брокере | Добавлено | После переноса relay внутрь consumer'а публикация зависит от этого процесса; молча умершая фоновая задача останавливает разгрузку outbox незаметно (RFC §5.2) |
| Порядок старта и проба готовности | Добавлено | Схему создаёт `api`, а `consumer` стартует параллельно: без пробы он обращается к несуществующим таблицам (RFC §11.1) |
| Ключи маршрутизации при публикации | Добавлено | Прежняя редакция задавала ключи только для обратного направления; публикация не по тому ключу теряется молча (RFC §7) |
| Долговечность при перезапуске брокера | Добавлено | Объявленные durable очереди без тома не переживают пересоздание контейнера (RFC §11.2) |
| Стабильность `event_id` | Добавлено | Дедупликация на стороне получателя, которую требует RFC §2.3, без этого невозможна |
| Краткое и полное представления, отказ при лишних знаках суммы | Добавлено | Ответ создания и ответ получения различаются составом; молчаливое округление денег недопустимо (RFC §8.1) |
| Приёмник с управляемым числом отказов | Добавлено | Без эндпоинта, отказывающего заданное число раз, пункт слайса 8 про успех после повторов нечем проверить снаружи |
| Ограничение адреса назначения webhook | Добавлено | ADR 0002 меняет решение RFC §10: оговорка писалась до появления отправки в коде, а сервис действительно ходит POST'ом изнутри сети по адресу клиента |
| Отвергнутый webhook уходит в DLQ | Добавлено | Молчаливое подтверждение оставляло платёж неуведомлённым без единого следа; заодно это исполнение пункта слайса 8 про недостижимый `webhook_url` |
| Snapshot OpenAPI | Добавлено | Требование §9 CLAUDE.md; заодно проверяет, что приёмник webhook не попал в публичную схему |

Прочие расхождения формулировок с исходным набором — редакционные и смысла пунктов не меняют.
