# Список тестов

**Статус:** на согласовании. После согласования замораживается и служит критерием готовности.
Добавление пункта по ходу работы — отдельным коммитом с пояснением.

Сценарии сформулированы на языке домена. Группировка по слайсам совпадает с RFC 0001.
Пометки: `[u]` unit — без I/O, `[i]` integration — реальные Postgres / RabbitMQ / HTTP,
`[e]` e2e — поднятый compose целиком.

---

## Слайс 1. Домен

- `[u]` новый платёж создаётся в статусе `pending`, `processed_at` пуст
- `[u]` переход `pending → succeeded` проставляет `processed_at` из `Clock`
- `[u]` переход `pending → failed` проставляет `processed_at` из `Clock`
- `[u]` переход из терминального статуса запрещён и поднимает ошибку домена
- `[u]` повторный переход в тот же терминальный статус запрещён
- `[u]` сумма, равная нулю или отрицательная, отвергается
- `[u]` валюта вне множества `{RUB, USD, EUR}` отвергается
- `[u]` `backoff(attempt)` возвращает `[2.0, 4.0, 8.0]` для попыток 1, 2, 3

## Слайс 2. Персистентность и outbox

- `[i]` сохранённый платёж читается обратно без потери суммы и точности
- `[i]` при создании платежа в outbox появляется ровно одно событие
- `[i]` платёж и событие пишутся атомарно: при откате нет ни одной строки
- `[i]` второй платёж с тем же `idempotency_key` не создаётся
- `[i]` два одновременных запроса с одним `idempotency_key` дают один платёж и одно событие
- `[i]` захват платежа в работу удаётся один раз; второй захват не проходит
- `[i]` захват с протухшим сроком удержания проходит повторно
- `[i]` выборка неопубликованных событий пропускает строки, занятые другим процессом
- `[i]` миграции накатываются и откатываются

## Слайс 3. API

- `[i]` создание платежа возвращает `202`, `payment_id`, статус `pending` и `created_at`
- `[i]` повторный запрос с тем же `Idempotency-Key` и тем же телом возвращает тот же `payment_id`
- `[i]` повторный запрос с тем же ключом не создаёт второе событие в outbox
- `[i]` тот же ключ с другим телом → `409`
- `[i]` порядок ключей в метаданных не влияет на признание тела совпадающим
- `[i]` запрос без `X-API-Key` → `401`
- `[i]` запрос с неверным `X-API-Key` → `401`
- `[i]` запрос без `Idempotency-Key` → `422`
- `[i]` невалидная валюта → `422`
- `[i]` сумма ≤ 0 → `422`
- `[i]` невалидный `webhook_url` → `422`
- `[i]` получение существующего платежа возвращает `200` и полное представление
- `[i]` получение несуществующего платежа → `404`
- `[i]` создание платежа не обращается к брокеру

## Слайс 4. Outbox relay

- `[i]` опубликованное событие помечается опубликованным и повторно не публикуется
- `[i]` если брокер не подтвердил публикацию, событие остаётся неопубликованным
- `[i]` если публикация упала, время следующей попытки сдвигается, а счётчик попыток растёт
- `[i]` недоступность брокера не приводит к потере события: оно уходит после восстановления
- `[i]` два одновременных relay не публикуют одно событие дважды

## Слайс 5. Consumer

- `[u]` успешная обработка переводит платёж `pending → succeeded`
- `[u]` неуспешная обработка переводит платёж `pending → failed`
- `[u]` исход эмуляции шлюза детерминирован: два вызова для одного платежа дают один результат
- `[i]` повторная доставка того же события не обращается к шлюзу второй раз
- `[i]` повторная доставка не меняет уже терминальный статус
- `[i]` повторная доставка при доставленном webhook не шлёт webhook второй раз
- `[i]` повторная доставка при недоставленном webhook повторяет только webhook
- `[i]` платёж со статусом `failed` подтверждается как обработанный и не уходит в DLQ

## Слайс 6. Webhook и retry

- `[u]` webhook содержит `event_id`, `payment_id`, статус, сумму, валюту и `processed_at`
- `[i]` при отказе webhook делается 3 попытки с растущей задержкой
- `[i]` успех со второй попытки не приводит к третьей
- `[i]` ответ `4xx` не повторяется
- `[i]` ответы `408` и `429` повторяются
- `[i]` успешная доставка фиксируется, и повторная обработка её не дублирует

## Слайс 7. DLQ

- `[i]` после исчерпания повторов сообщение уходит в DLQ
- `[i]` сообщение с неразбираемым телом уходит в DLQ сразу, минуя повторы
- `[i]` сообщение из retry-очереди по истечении задержки возвращается в основную очередь
- `[i]` счётчик попыток растёт от повтора к повтору
- `[i]` сообщение в DLQ несёт причину отказа и идентификатор платежа

## Слайс 8. Сквозной

- `[e]` платёж, созданный через API, доходит до терминального статуса, и webhook приходит
- `[e]` окружение поднимается с нуля и схема БД создаётся автоматически
- `[e]` платёж, созданный при остановленном брокере, обрабатывается после его запуска

## Изменения относительно исходного списка

Пункты ниже уточнены или добавлены по итогам ревью дизайна; обоснование — в RFC 0001.

| Пункт | Что изменилось | Почему |
|---|---|---|
| «повторная доставка не шлёт webhook второй раз» | Разделён на два: при доставленном webhook — не шлёт, при недоставленном — повторяет | Иначе платёж с недоставленным webhook не будет уведомлён никогда, и retry обработки теряет смысл (RFC §9) |
| relay и подтверждение публикации | Добавлено | Без проверки подтверждения outbox не даёт гарантии: потерянное сообщение считается доставленным (RFC §2) |
| неразбираемое тело сообщения | Добавлено | Валидация происходит до тела обработчика, и такое сообщение обходит весь механизм повторов (RFC §6.3) |
| возврат из retry-очереди в основную | Добавлено | Единственный способ поймать незаданный ключ маршрутизации при dead-letter, из-за которого цепочка молча уничтожает сообщения (RFC §7) |
| два одновременных запроса с одним ключом | Добавлено | Гонка на уникальном ключе — типовой сценарий проверки (RFC §8) |
| `backoff(attempt)` | Добавлено | Требование §6 CLAUDE.md: задержка проверяется как чистая функция, без реального ожидания |
