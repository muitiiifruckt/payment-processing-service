# Payment Processing Service

Микросервис асинхронной обработки платежей: принимает запросы на оплату, обрабатывает их
через эмуляцию внешнего платёжного шлюза и уведомляет клиента о результате через webhook.

**Стек:** FastAPI + Pydantic v2, SQLAlchemy 2.0 (async), PostgreSQL, RabbitMQ (FastStream),
Alembic, Docker Compose.

Решения и их обоснование — в `docs/rfc/0001-payment-processing.md`; изменения решений —
в `docs/adr/`. Список сценариев, по которому проверялась готовность, — `docs/test-list.md`.

## Запуск

```bash
cp .env.example .env
docker compose up -d --build --wait
```

Поднимаются ровно четыре сервиса: `postgres`, `rabbitmq`, `api`, `consumer`. Миграции
накатывает `api` перед стартом, `consumer` дожидается его готовности. Relay публикации
из outbox — фоновая задача внутри `consumer`, отдельным сервисом не выносится.

API — на `http://localhost:8000`, интерактивная схема — `/docs`.

Адреса `webhook_url` внутри периметра по умолчанию запрещены (ADR 0002), поэтому уведомление
на `localhost` вашей машины по умолчанию не дойдёт. Чтобы разрешить, добавьте хост в
`WEBHOOK_ALLOWED_HOSTS` — в `.env.example` для этого есть закомментированная строка с
`host.docker.internal`. Список снимает проверку с хоста целиком, поэтому по умолчанию в нём
только демонстрационный приёмник. Публичные адреса работают без всякого списка.

Остановка с удалением данных:

```bash
docker compose down -v
```

## Примеры запросов

Аутентификация — заголовок `X-API-Key` (значение из `.env`). Ключ идемпотентности —
`Idempotency-Key`, обязателен.

### Создание платежа

```bash
curl -X POST http://localhost:8000/api/v1/payments \
  -H "X-API-Key: local-dev-key" \
  -H "Idempotency-Key: 6f1c2b7a-0b1e-4f7a-9c2d-8a1b2c3d4e5f" \
  -H "Content-Type: application/json" \
  -d '{
  "amount": "100.50",
  "currency": "RUB",
  "description": "Оплата заказа 42",
  "metadata": {
    "order_id": "42"
  },
  "webhook_url": "http://api:8000/__sink__/webhook"
}'
```

Ответ `202`:

```json
{
  "payment_id": "0192f3a4-0000-7000-8000-000000000001",
  "status": "pending",
  "created_at": "2026-08-19T12:00:00+00:00"
}
```

`webhook_url` необязателен: платёж без него обрабатывается штатно и считается уведомлённым.

### Получение платежа

```bash
curl http://localhost:8000/api/v1/payments/0192f3a4-0000-7000-8000-000000000001 \
  -H "X-API-Key: local-dev-key"
```

```json
{
  "payment_id": "0192f3a4-0000-7000-8000-000000000001",
  "amount": "100.50",
  "currency": "RUB",
  "description": "Оплата заказа 42",
  "metadata": {"order_id": "42"},
  "status": "succeeded",
  "webhook_url": "http://api:8000/__sink__/webhook",
  "created_at": "2026-08-19T12:00:00+00:00",
  "processed_at": "2026-08-19T12:00:04+00:00"
}
```

### Коды ответов

| Ситуация | Код |
|---|---|
| Платёж создан | `202` |
| Тот же `Idempotency-Key` и то же тело | `202`, полное представление с фактическим текущим статусом |
| Тот же `Idempotency-Key` и другое тело | `409` |
| Нет `X-API-Key` или ключ неверный | `401` |
| Нет `Idempotency-Key` или тело невалидно | `422` |
| Платёж не найден | `404` |

## Как это работает

1. `POST` пишет платёж и событие в outbox **одной транзакцией**. Публикация в брокер прямо
   из обработчика сделала бы outbox бессмысленным, поэтому её там нет.
2. Relay внутри `consumer` забирает неопубликованные события пачками и публикует в
   `payments.new`, помечая отправленным только после подтверждения брокера.
3. `consumer` захватывает платёж, идёт в эмуляцию шлюза (2–5 секунд, 90/10), записывает
   исход и отправляет webhook.
4. Доставка — **at-least-once**. Повторная доставка того же события не меняет статус и не шлёт
   webhook второй раз, **если предыдущий был доставлен**; недоставленный она добьёт одной
   попыткой. Исход шлюза детерминирован по `payment_id`, отметка о доставке ставится в базе.

   **Получатель webhook обязан дедуплицировать по `event_id`** — это часть контракта. Тело
   несёт `event_id`, `event_type`, `payment_id`, статус, сумму строкой, валюту и `processed_at`.

### Повторы

Три независимых механизма, у каждого свои задержки:

| Что повторяется | Сколько | Задержки |
|---|---|---|
| Отправка webhook | 3 попытки на первом прогоне, 1 на повторных | 1 с, 2 с |
| Обработка сообщения | 3 повтора через retry-очереди | 2 с, 4 с, 8 с |
| Публикация из outbox | до успеха | экспоненциально, потолок 60 с |

После неуспеха четвёртого прогона обработчика сообщение уходит в `payments.new.dlq` с
причиной отказа, классом отказа, `payment_id` и номером прогона в заголовках.

Сам по себе бизнес-отказ (`failed`) отказом обработки не является: статус записан, сообщение
подтверждено. В DLQ такой платёж всё же может попасть — но не из-за исхода, а если не удалось
уведомить получателя: адрес запрещён, отвергнут им же или недостижим после всех повторов.

## Демонстрационный приёмник webhook

При `ENABLE_WEBHOOK_SINK=true` в `api` включается приёмник на `/__sink__/webhook`: `POST`
складывает событие в память (это делает `consumer`, ключа он не знает), `GET` показывает
последние сто и требует `X-API-Key` — наружу это содержимое чужих платежей. Асимметрия
намеренная, но означает, что писать в приёмник может кто угодно, кто дотянулся до порта.

Для проверки повторов есть `POST /__sink__/flaky/{n}`: отказывает `n` раз на каждый платёж,
потом принимает. `GET /__sink__/flaky` под ключом показывает счётчик обращений. В `webhook_url` его нужно
указывать так, как его видит `consumer` — `http://api:8000/__sink__/webhook`: `localhost`
внутри сети compose означает сам `consumer`. В публичную схему он не
попадает и нужен только для демонстрации и сквозных тестов.

## Тесты

```bash
uv sync
uv run pytest -m "not integration and not e2e"   # быстрые, меньше секунды
uv run pytest -m integration                     # нужен docker: postgres и rabbitmq
uv run pytest -m e2e                             # нужно поднятое окружение
```

Интеграционные тесты поднимают контейнеры сами (testcontainers). Если Postgres или RabbitMQ
уже подняты, укажите `TEST_DATABASE_URL` и `TEST_RABBITMQ_URL`.

## Известные ограничения

- **Защита `webhook_url` от подмены DNS неполная.** Адрес проверяется перед отправкой:
  переадресации не выполняются, таймаут 5 секунд, тело ответа читается не дальше 64 КБ,
  а имя разрешается и отвергается, если указывает внутрь периметра — приватные диапазоны,
  loopback, link-local, включая `169.254.169.254` (ADR 0002). Незакрытым остаётся окно между
  проверкой и подключением: httpx резолвит имя заново, и запись в DNS за это время может
  измениться. Исключения задаёт `WEBHOOK_ALLOWED_HOSTS` — в демо-окружении там `api`,
  иначе приёмник внутри сети compose недостижим.
- **Повторная доставка терминального платежа не сериализуется захватом.** Если webhook не
  доставлен, повтор может совпасть по времени с ещё идущей первой отправкой. Оба обращения
  несут один `event_id`, то есть дедуплицируются на стороне получателя — это ровно та
  гарантия at-least-once, которую объявляет RFC §2.
- **После потери данных брокера consumer нужно перезапустить.** Топология объявляется на
  старте процесса, а у retry-очередей и DLQ нет подписчиков — переподключение само по себе
  их не вернёт. Штатный перезапуск брокера с томом этого не требует.
- **Опубликованные строки outbox не удаляются.** Таблица растёт линейно по числу платежей;
  периодическая чистка старых записей за границами задания.
- **Уведомления едут по тому же каналу, что и обработка.** Недоставленный webhook по успешно
  проведённому платежу уводит сообщение в DLQ, где оно соседствует с настоящими отказами
  обработки. Отдельная очередь доставки уведомлений развела бы это чище — продуктовое
  улучшение за границами задания.
- **Приёмник webhook хранит события в памяти** и переживает только время жизни процесса.
